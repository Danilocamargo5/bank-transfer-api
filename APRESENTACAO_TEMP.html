🏦 Bank Transfer API - Apresentação Técnica

📋 Visão Geral

Microserviço Spring Boot em Kotlin que processa transferências bancárias com garantias de atomicidade, idempotência e resiliência usando DynamoDB, Kafka e SQS.

Status: ✅ 104 testes passando | 🔒 Distributed Locks | 📊 Transações unificadas | 📝 MDC + JSON Logs

🏗️ Classes Principais

1. TransferService (application/)

Responsabilidade: Orquestradora do fluxo completo

  • Adquire locks distribuídos (previne race conditions)
  • Valida idempotência (transferId único)
  • Valida regras de negócio (saldo, conta ativa)
  • Salva em transação unificada (3 writes atomicamente)
  • Gerencia retries (3x com backoff exponencial)
  • Envia falhas críticas para DLQ
  • Correlaciona logs via MDC (transferId)

2. LockService (infrastructure/service/)

Responsabilidade: Gerenciador de locks distribuídos

  • Cria tabela automaticamente (no init)
  • Adquire locks via PutItem + ConditionExpression (atômico)
  • Retry com backoff (5 tentativas)
  • TTL 10s (auto-cleanup)
  • Release em ordem LIFO (previne deadlock)

3. TransferRepository (infrastructure/repository/)

Responsabilidade: Persistência de transferências

  • saveTransferWithAccountsAtomically() - NOVO: Transação unificada com 3 writes
  • hasCompletedTransfer() - Verifica idempotência
  • findByTransferId() - Query por transferId

4. AccountRepository (infrastructure/repository/)

Responsabilidade: Persistência de contas

  • saveAtomically() - Salva múltiplas contas
  • findById() - Busca conta
  • existsById() - Validação

5. TransferKafkaConsumer (infrastructure/messaging/)

Responsabilidade: Consumer de eventos Kafka

  • Consome de transfer-requested
  • Manual ACK (offset só avança on sucesso)
  • Publica resultado em transfer-completed ou transfer-failed
  • MDC: correlaciona com transferId

6. DeadLetterService (infrastructure/service/)

Responsabilidade: Gerenciar falhas críticas via SQS

  • Envia para DLQ quando save/rollback falha
  • Preserva informação completa para investigação
  • Separa transfer-failed (negócio) de transfer-failed-dlq (crítico)

7. TransferValidator (domain/validator/)

Responsabilidade: Validação de dados

  • Valida formato (transferId, accountIds)
  • Valida amount e currency
  • Previne mesma conta origem/destino

8. TransferMetrics (infrastructure/metrics/)

Responsabilidade: Coleta de métricas

  • Tempo de processamento (P50, P95, P99)
  • Contagem de sucessos/falhas
  • Falhas por tipo

🔄 Fluxo de Transferência

1. [Kafka] transfer-requested
   ↓
2. [TransferKafkaConsumer] desserializa
   ↓
3. [TransferService.processTransfer()]
   ├─ [LockService] acquireTransferLocks()
   ├─ Valida idempotência + regras
   ├─ Debita/Credita
   ├─ [TransferRepository] saveTransferWithAccountsAtomically()
   │  └─ 1 transação: source + dest + transfer
   ├─ [LockService] releaseLocks() (LIFO)
   └─ Publica transfer-completed
   
4. Se erro: transfer-failed
   ├─ Se crítico: DLQ
   └─ Salva com status FAILED

🔒 Distributed Locking

Como funciona:

  • PutItem com ConditionExpression: "attribute_not_exists(lockId)"
  • Atômico - ou consegue lock ou falha
  • Retry 5x com backoff exponencial
  • LIFO release (previne deadlock)
  • TTL 10s (auto-cleanup)

📊 Transações Unificadas

Antes: 2 transações separadas (contas + transfer) → risco de inconsistência
Depois: 1 transação com 3 writes → all-or-nothing garantido
